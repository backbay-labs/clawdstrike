# Policy Anatomy

Policies are YAML files that define which guards are active and how they are configured.
They control the boundary between an AI agent and the actions it can take. Every action
an agent attempts -- reading a file, making a network request, running a shell command --
passes through the policy engine, which consults the active policy to decide whether the
action is allowed.

In this lesson you will learn the structure of a ClawdStrike policy from the ground up.

## Schema Version

Every policy starts with a `version` field that declares which schema version it uses:

```yaml
version: "1.5.0"
```

## Top-Level Fields

A policy has a handful of top-level fields:

```yaml
version: "1.5.0"
name: My Policy
description: A brief description of what this policy is for

extends: clawdstrike:default    # Optional: inherit from a built-in ruleset
merge_strategy: deep_merge      # How child overrides combine with parent

guards:
  # Per-guard configuration (13 built-in guards)

settings:
  fail_fast: false
  verbose_logging: false
  session_timeout_secs: 3600
```

- **`version`** -- Schema version string (required).
- **`name`** -- Human-readable name for the policy.
- **`description`** -- What this policy is for and when to use it.
- **`extends`** -- Inherit from a built-in ruleset, a local file, a remote URL, or a git ref.
- **`merge_strategy`** -- Controls how child fields combine with parent fields (`deep_merge`, `merge`, or `replace`).
- **`guards`** -- The main configuration block. Each key is a guard name.
- **`settings`** -- Engine-level settings that apply across all guards.

## Interactive Editor

Use the editor below to explore a valid policy. Try modifying it -- for example, add an
unknown field like `foobar: true` at the top level and watch the red underline appear.
You can also try adding an invalid field inside a guard config to see the error message:

<PolicyEditor defaultValue={`version: "1.5.0"

guards:
  forbidden_path:
    patterns:
      - "**/.ssh/**"
      - "**/.aws/**"
      - "**/.env"
    exceptions: []

  egress_allowlist:
    allow:
      - "api.github.com"
      - "registry.npmjs.org"
    block: []
    default_action: block

settings:
  fail_fast: false
  verbose_logging: false
  session_timeout_secs: 3600
`} />

Try these experiments:

1. Add `foobar: true` at the top level -- the editor rejects unknown fields
2. Change `fail_fast` to `"yes"` instead of `false` -- type validation catches it
3. Remove the `version` field -- the editor flags the missing required field
4. Add `enabled: true` inside `forbidden_path` -- a valid field you might not have known about

## The Settings Block

The `settings` block controls engine-level behavior:

- **`fail_fast`** -- When `true`, the engine stops evaluating after the first guard denial.
  When `false` (the default), all guards run and the aggregate result is returned. Setting
  this to `false` is usually better during development because you see all violations at once.
- **`verbose_logging`** -- Enables detailed logging of each guard evaluation. Useful for
  debugging but noisy in production.
- **`session_timeout_secs`** -- How long a session can remain active before requiring
  re-authentication. Defaults to 3600 (one hour).
