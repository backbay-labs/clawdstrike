# Security Regression: URL Spoofing

Security is a cat-and-mouse game. Even well-designed guards can have blind spots.
This lesson walks through a real security regression from ClawdStrike's test suite --
a URL spoofing attack that tricked the egress allowlist guard.

## The Attack

RFC 3986 defines the syntax of URIs. One feature most developers forget about is
the **userinfo** component:

```text
https://user:password@host/path
        ^^^^^^^^^^^^^^
        This is "userinfo" -- everything before the @
```

A clever attacker exploits this by crafting:

```text
https://api.openai.com:443@evil.example/path
```

To a naive URL parser, the host looks like `api.openai.com`. But the **real** host
is `evil.example`. The `api.openai.com:443` part is just the userinfo -- a username
that happens to look like a trusted domain.

## Why It Matters

If the egress allowlist guard checks the *apparent* host (`api.openai.com`) instead
of the *real* host (`evil.example`), the attacker can exfiltrate data to any domain
by prepending an allowed domain as userinfo.

The attacker's request looks like it's going to a trusted API. In reality, it's
sending your data to `evil.example`. The guard sees `api.openai.com` in the URL
and waves it through.

This is not a theoretical attack. URL userinfo spoofing has been used in real-world
phishing and data exfiltration campaigns.

## The Vulnerable Code

A naive host extraction function might look like this:

```rust
// VULNERABLE: naive host extraction
fn extract_host_naive(url: &str) -> Option<&str> {
    let without_scheme = url.strip_prefix("https://")?;
    // Takes everything before the first '/' or ':'
    // Would return "api.openai.com" for the spoofed URL!
    without_scheme.split(&['/', ':'][..]).next()
}
```

This function strips the scheme and grabs the first segment. For
`https://api.openai.com:443@evil.example/path`, it returns `api.openai.com` --
exactly what the attacker wants.

## The Lesson

Every parser bug is a potential bypass. URL parsing, path normalization, header
injection, encoding edge cases -- attackers exploit the gap between what code
*appears* to do and what it *actually* does.

Three rules from this regression:

1. **Never roll your own parser.** Use well-tested libraries for URL parsing, path
   normalization, and any format with a spec.
2. **Write regression tests for every security fix.** The test is the proof that the
   fix works and the guarantee that the bug won't return.
3. **Think in RFC, not in vibes.** If you're writing security-critical code, read the
   spec. RFC 3986 section 3.2.1 defines userinfo. If you didn't know that section
   existed, your parser probably doesn't handle it correctly.
